# 09 代码规模约束与文件规划

## 1. 硬性约束（验收指标，不可违反）

| 指标 | 约束 | 合规区间 | 本项目目标 |
| --- | --- | --- | --- |
| Go 代码行数（**不含测试**） | `2000 < L < 2200` | 2001 ~ 2199 | **2150**（±20 容差） |
| Go 代码文件数（**不含测试**） | `20 < F < 25` | 21 ~ 24 | **23** |

- "测试代码"定义为文件名以 `_test.go` 结尾的文件，**完全不计入**；
- 前端（`web/*`）、SQL 迁移、Makefile、脚本、配置文件不计入；
- 该约束由 `make verify` 中的计量脚本**强制校验**，不达标即构建失败（fail-fast）。

## 2. 计量口径（脚本 `scripts/linecount.sh`）

```bash
#!/usr/bin/env bash
# 用法: scripts/linecount.sh   → 输出行数与文件数，越界时退出码非 0
set -euo pipefail
ROOT="$(cd "$(dirname "$0")/.." && pwd)"

# 1) 收集所有非测试 .go 文件
mapfile -t FILES < <(cd "$ROOT" && find . -name '*.go' ! -name '*_test.go' -type f | sort)

# 2) 文件数
FCOUNT=${#FILES[@]}

# 3) 行数（物理行，wc -l 口径）
LINES=0
for f in "${FILES[@]}"; do
  n=$(wc -l < "$ROOT/$f")
  LINES=$((LINES + n))
done

echo "Go non-test files: $FCOUNT (required 21..24)"
echo "Go non-test lines: $LINES (required 2001..2199)"

# 4) 越界判定
if [ "$FCOUNT" -lt 21 ] || [ "$FCOUNT" -gt 24 ]; then exit 1; fi
if [ "$LINES" -lt 2001 ] || [ "$LINES" -gt 2199 ]; then exit 1; fi
```

> 口径说明：按 `wc -l` 物理行统计（含空行与注释行），**预算表即按此口径估算**，保证"估多少、数多少"一致。若实现阶段采用"忽略空行/注释"口径，需同步调整预算并重估本表。

## 4. 预算制定原则

1. **自然填充，不注水**：预算来自 05 文档的业务逻辑展开——每个文件的行数=该职责的算法/分支/错误处理自然体量，禁止用无意义空行凑数；
2. **纯逻辑层占比 ≥ 40%**：matcher + responder + service 合计 1005 行，占 47%，保证约束不挤压核心逻辑表达空间；
3. **薄 handler、瘦 worker**：handler 只做参数解析与响应封装，worker 只做调度，业务判断全部下沉 service；
4. **预留弹性 ±20 行**：实现时以 2150 为基准，允许 2130~2170；极端情况触碰 2001 或 2199 边界即触发下文熔断流程。

## 5. 超限熔断与调整流程

| 情形 | 处理 |
| --- | --- |
| `L < 2001`（偏少） | ① 优先补 matcher/responder 边界分支（如 JSONPath 错误路径、模板转义）；② 补 admin_handler 参数校验分支；③ 在预算表登记追加来源后重跑计量 |
| `L > 2199`（偏多） | ① 优先压缩 repository 层重复 SQL（抽公共行扫描/参数拼接 helper）；② 压缩 handler 中可复用的响应封装；③ **禁止**删测试、禁止合并文件降文件数 |
| `F < 21` | 拆分职责：如把 scenario 快照构建拆出独立文件、把 cron 匹配拆到 matcher 侧 |
| `F > 24` | 合并同类：如 stats_repo 并入 record_repo、cleaner 并入 tasks.go（本项目规划已按 23 文件预留 1 个弹性） |

**变更纪律**：任何影响行数/文件数的实现决策，必须在合并前同步更新本表（含备注原因），并保证 `make verify` 全绿。

## 6. 与"不得做成简易 Mock"的呼应

行数预算的分配本身即体现工程完整性：

- 迁移与数据库层（database + repository）占 420 行（20%）——满足"数据库迁移"硬要求；
- 纯逻辑引擎（matcher + responder）占 455 行（21%）——满足"配置请求匹配、动态响应"的算法要求；
- 场景与记录服务占 215 行（10%）——满足"场景切换、调用记录"的状态管理要求；
- 后台任务占 175 行（8%）——满足"后台任务"硬要求；
- 入口/中间件/装配占 265 行（12%）——满足"API 与完整构建验证"。

一个简易 Mock 不可能达到上述分布，从而在结构上保证本项目**不是简易 Mock**。
