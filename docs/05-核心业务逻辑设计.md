# 05 核心业务逻辑详细设计

本文档对五大核心业务能力做逻辑级详细设计：**请求匹配、动态响应、场景切换、调用记录、延迟故障**。每个能力给出：输入/输出、数据结构、算法步骤、边界情况与伪代码。

---

## 1. 请求匹配引擎（Matcher）

### 1.1 职责
给定一个入站 HTTP 请求与一批契约（含各自生效场景的匹配规则），输出**唯一命中结果**或"未命中"。纯逻辑、无 IO，可单测。

### 1.2 数据结构
```go
// 契约快照（模拟热路径只读对象）
type ContractSnapshot struct {
    Key      string
    Priority int
    Enabled  bool
    Scenario ScenarioSnapshot // 当前生效场景快照
}

// 场景快照（不可变，切换时整体重建）
type ScenarioSnapshot struct {
    ID            int64
    Name          string
    Rules         MatchRules
    Response      ResponseDef
    Delay         DelayDef
    Fault         FaultDef
    Switch        SwitchDef
    HitCount      int64 // 快照生成时的命中次数（after_calls 判定用）
}

type MatchRules struct {
    Method  string           // "GET" 或 "*"
    Path    string           // "/api/v1/user/{id}"，支持 * 与 /**
    Headers []KeyValueRule   // AND
    Query   []KeyValueRule   // AND
    Body    []JSONPathRule   // AND（jsonpath + expected）
}

type KeyValueRule struct {
    Name  string // 键名（头/查询参数名），* 通配任意
    Value string // 期望值，支持尾通配 "test-*" 与 * 任意
}

type JSONPathRule struct {
    Path  string // "$.userId"、"$.items[0].id"
    Value string // 期望值（字符串比较；数字/布尔先规范化为字符串）
}
```

### 1.3 匹配算法

```
输入: 请求 R（method/path/query/headers/body）、契约快照列表 C[]
输出: 命中结果 {contractKey, scenario, matchDetail} 或 nil

1. 候选集 = [c for c in C if c.Enabled]
2. 对候选集排序: priority 降序 → created_at 升序（快照内携带）→ key 升序
3. for c in 候选集:
      s = c.Scenario
      detail = []
      if !methodMatch(R.Method, s.Rules.Method): continue
      if !pathMatch(R.Path, s.Rules.Path, &pathParams): continue   // 产出路径参数
      if !headersMatch(R.Header, s.Rules.Headers): continue
      if !queryMatch(R.URL.Query(), s.Rules.Query): continue
      if !bodyMatch(R.Body, s.Rules.Body): continue
      return 命中(c.Key, s.Name, detail)
4. return nil  // 未命中
```

### 1.4 各维度匹配规则

| 维度 | 规则 | 示例 |
| --- | --- | --- |
| 方法 | 相等或 `*` | `method=*` 命中任意方法 |
| 路径 | ①精确相等 ②`{name}` 匹配一段并捕获 ③`*` 匹配单段 ④尾 `/**` 匹配剩余 | `/api/v1/user/{id}` 命中 `/api/v1/user/88`，`id=88`；`/files/**` 命中任意子路径 |
| 头 | 键名相等（大小写不敏感）+ 值匹配（支持 `*` 尾通配） | `X-Token: test-*` |
| 查询 | 键名精确 + 值匹配（支持 `*`）；多值取第一个 | `type=vip` |
| JSON Body | 先解析 body 为通用 JSON（`map[string]any`/`[]any`），按 JSONPath 取值，再与期望值比较 | `$.userId=1001` 命中 `{"user":{"id":1001}}` 与 `{"userId":1001}` 两种路径写法需按实际路径配置 |

**JSONPath 简化实现**：仅支持 `$`、`.`字段、`[N]`下标、`[*]`任意元素；解析失败即条件不满足。

### 1.5 边界与业务规则
- Body 非合法 JSON 时，含 body 条件的规则**不命中**（不 panic）；
- 匹配 detail 文案示例：`"priority=100 matched: method,path,body"`，未命中维度列出未满足项；
- 路径参数捕获结果注入渲染上下文（`{{path.id}}`）；
- 全部未命中返回 40400（BR-4 保证顺序稳定）。

## 2. 动态响应引擎（Responder）

### 2.1 职责
根据命中的场景响应定义与请求上下文，渲染出最终 `{status, headers, body}`；渲染失败走 fallback。

### 2.2 请求上下文（注入模板的数据）
```go
type RenderContext struct {
    Method  string
    Path    string
    Query   map[string]string   // 查询参数
    Headers map[string]string   // 请求头
    Body    any                // 解析后的 JSON，nil 表示非 JSON
    PathParams map[string]string
    State   map[string]any     // 场景状态（含 counter 等，来自场景快照）
}
```

### 2.3 模板语法

| 语法 | 示例 | 求值 |
| --- | --- | --- |
| `{{request.method}}` | `GET` | 请求方法 |
| `{{request.path}}` | `/api/v1/user/88` | 原始路径 |
| `{{request.query.name}}` | 查询参数 `name` 值 | 缺失→空串 |
| `{{request.header.X-Token}}` | 请求头（大小写不敏感） | 缺失→空串 |
| `{{request.body.userId}}` | JSONPath 简式（`$.` 省略） | 缺失→空串 |
| `{{path.id}}` | 路径参数 | 未捕获→空串 |
| `{{state.counter}}` | 场景状态 | 缺失→空串 |
| `{{uuid()}}` | `f47ac10b-...` | 随机 UUID v4 |
| `{{now()}}` | `2025-08-23T14:30:00Z` | 当前 UTC 时间 |
| `{{timestamp()}}` | `1784860200` | 当前 Unix 秒 |
| `{{randInt(1,100)}}` | `42` | [1,100] 随机整数 |
| `{{randStr(8)}}` | `aZ9kQ2mX` | 8 位随机字母数字 |
| `{{randomFrom(a,b,c)}}` | `b` | 从列表随机取一个 |
| `{{echo(body)}}` | 原样回显请求体 | 调试用 |

**求值顺序**：正则扫描所有 `{{...}}`，逐个求值替换；未识别语法原样保留并计入渲染告警（fallback 判定依据之一）。

### 2.4 渲染流程

```
输入: ResponseDef{status, headers, body模板}, RenderContext
输出: {status, headers, body} 或 error

1. body = templateRender(body模板, ctx)      // 纯字符串替换
2. 若 body 非空且响应头声明 application/json：
     json.Valid([]byte(body)) 不通过 → 记告警（不阻塞，交由调用方按 fallback 策略处理？）
3. headers = 对每个响应头模板值做同样的变量替换
4. status 按配置（模板可为 "{{path.code}}" 场景化状态码，求值为 200~599 合法数字）
5. 若 body 长度 > 1MB → error "response body too large"
返回
```

**Fallback（FR-3.4）**：渲染任一环节 error 时，使用场景的兜底配置：默认 `500 + {"code":50000,"message":"render failed: <原因>"}`；渲染错误同时写入调用记录 `match_detail` 备注。

### 2.5 边界与业务规则
- 模板值中含字面 `{{` 时使用 `\{{` 转义，转义符不参与输出；
- 响应头默认注入 `Content-Type: application/json; charset=utf-8`（场景未显式声明时）；
- 状态码非法（<100 或 >599）→ fallback 500。

## 3. 场景切换（Scenario Switching）

### 3.1 场景状态机

```
                    activate (manual / cron / after_calls)
      ┌────────────────────────────────────────────────────────┐
      ▼                                                         │
┌──────────┐   删除当前生效场景时    ┌──────────┐
│ 生效场景  │◀─────────────────────│ 默认场景  │
│ (is_active)│  自动回退为生效        │          │
└──────────┘                        └──────────┘
```

### 3.2 快照机制（ADR-2 落地）

`ScenarioService` 维护 `sync.Map`（key=contract_key）或单一 `atomic.Value` 指向 `map[string]ContractSnapshot`：

```
切换场景(contractKey, toScenarioId, trigger):
  1. 事务内: 清 is_active → 设 to 为 is_active → 写 switch_logs
  2. 事务提交成功后: 重建该契约快照（读取最新场景定义）
  3. 原子替换: snapshotStore.Store(contractKey, newSnapshot)   // 并发请求 Load 到旧/新快照，均为完整一致
```

**命中计数与 after_calls（FR-4.3）**：
```
命中请求处理中（事务内）:
  UPDATE scenarios SET hit_count = hit_count + 1 WHERE id = 当前场景id
  SELECT hit_count, switch_after_calls, switch_to_scenario_id FROM scenarios WHERE id = ?
  if switch_after_calls > 0 AND hit_count >= switch_after_calls:
      执行切换(同事务) → 触发方式 after_calls → 写 switch_logs
  commit
```
- 说明：命中计数与切换判定在同一事务，天然串行，避免并发双切换；
- 快照中的 `HitCount` 仅用于渲染 `{{state.counter}}`（展示"第几次"）。

### 3.3 触发方式汇总

| 触发 | 方式 | 入口 |
| --- | --- | --- |
| manual | 管理 API activate | `POST /admin/api/contracts/{key}/scenarios/{id}/activate` |
| after_calls | 命中计数达标（事务内自动） | 模拟热路径 |
| cron | 后台调度器按 cron 表达式扫描并切换 | worker/scheduler + scenario_service |

### 3.4 边界与业务规则
- 切换目标场景不存在 → 40900，不产生任何副作用；
- 切换默认场景为生效场景 → 直接置 is_active=1 即可（无 from 变更也记录日志）；
- 同一契约同时配置 after_calls 与 cron 时**互不排斥**，各自可触发（以日志区分 trigger_type）；
- 快照重建失败（DB 异常）时保留旧快照，保证模拟入口不中断（best-effort，告警日志）。

## 4. 调用记录（Call Records）

### 4.1 写入链路（异步，ADR-3 落地）

```
请求进入 → 生成 request_id（req_<hex16>）
处理完成（含未命中） → 构造 CallRecord（体截断 64KB）
  → select { case recordChan <- rec: 默认; default: 降级同步直写+告警计数 }
后台批量写入协程:
  for { 累积 ≤100 条 或 200ms 到期 → 单事务批量 INSERT → 成功则清空缓冲 }
```
- 队列容量 4096；批量写失败时**丢弃该批并记录告警计数**（BR-7：不影响模拟响应）；
- 批量 INSERT 使用多值语法 `INSERT INTO call_records (...) VALUES (...),(...)...`，单条构造 SQL 由 repository 完成。

### 4.2 记录内容组装

| 字段 | 来源 |
| --- | --- |
| method/path/query/headers/body/client_ip | 请求（body 读取后需重置以便再次消费，采用 `io.TeeReader` + 限制 64KB） |
| contract_key/scenario_name/matched/match_detail | MockService 匹配结果 |
| response_status/headers/body | 写出内容（包装 ResponseWriter 捕获） |
| injected_delay_ms/injected_fault | 故障/延迟注入结果 |
| total_ms | 处理开始到写出完成 |

### 4.3 查询逻辑
- 过滤条件 AND 组合：contract_key 精确、status 精确、matched 布尔、时间范围、keyword 对 body/path 模糊；
- `ORDER BY id DESC LIMIT ? OFFSET ?`；total 用 `COUNT(*)` 同条件查询；
- 大表查询必须走索引（created_at/contract_key/status 均有索引，见 03 文档）。

### 4.4 边界与业务规则
- 未命中请求也记录（`matched=false`），用于观察"哪些契约没配好"；
- 请求/响应体统一 UTF-8 截断，非法 UTF-8 转义为 `\ufffd`；
- 记录接口不返回体超过 4KB 的字段完整值（列表接口裁剪），详情接口返回全量。

## 5. 延迟与故障注入（Latency & Fault Injection）

### 5.1 注入顺序（BR-5）
```
渲染响应 → ① 故障判定 → ② 延迟等待 → ③ 写出
```
原因：故障响应不等待延迟（快速失败）；延迟只作用于最终写出的那个响应。

### 5.2 故障判定（FaultDef）
```
判定(场景故障配置, 当前命中序号 hitSeq):
  if !fault.enabled: return 无故障
  // ① 序号故障优先
  if hitSeq in fault.on_calls: return 故障{fault.status, fault.body, reason:"on_calls"}
  // ② 概率故障
  if fault.rate > 0 and rand.Float64() < fault.rate: return 故障{..., reason:"rate"}
  return 无故障
```
- 命中序号 = 该场景自启用以来的累计命中次数（hit_count，事务内自增后读取），保证 on_calls 语义稳定；
- `abort_connection=true`（FR-6.4）：不走 ①②，直接 `hijack` 关闭连接，记录 `injected_fault=true, reason:"abort"`。

### 5.3 延迟注入（DelayDef）
```
delay_ms = 0
if fixed_ms > 0: delay_ms = fixed_ms
elif min_ms>0 and max_ms>=min_ms: delay_ms = rand.Intn(max_ms-min_ms+1)+min_ms
if delay_ms > 0: time.Sleep(delay_ms)
```
- 上限保护：单次延迟最大 10s（配置超限按 10s 处理），防止误配打爆测试；
- 延迟写入 `injected_delay_ms`。

### 5.4 边界与业务规则
- 故障响应与正常响应一样可被记录、统计（fault_calls 计数）；
- 概率故障用 `math/rand`（非加密随机，性能优先），进程内单实例随机源；
- 故障响应体同样支持模板渲染（复用 responder），渲染失败用配置的原始故障体。

## 6. 模拟主流程（MockService.Handle）整合

```
Handle(w, r, requestID) → 输出响应（含延迟/故障/记录）

1. start = now
2. body = readBodyLimited(r, 64KB)   // TeeReader 保留原始流
3. snapshot = scenarioService.GetSnapshotForRequest(r)  // 或按需 Load 全部快照并匹配
4. match = matcher.Match(r, snapshotList)
5. if match == nil:
      w.WriteHeader(404); 写 40400 信封; record(matched=false); return
6. ctx = buildRenderContext(r, body, match.PathParams, match.Scenario.State)
7. resp, err = responder.Render(match.Scenario.Response, ctx)
   if err: resp = fallback(match.Scenario); matchDetail += ";render_failed"
8. fault = faultJudge(match.Scenario.Fault, match.Scenario.HitCount+1)
9. if fault.abort: hijack 关闭连接; record(injected_fault); return
10. delay = delayCalc(match.Scenario.Delay); if fault: resp = faultResp
11. if delay>0: sleep(delay)
12. writeResp(w, resp)   // 状态码/头/体
13. record(全部字段, totalMs=now-start)   // 异步
```

> 注意：第 7~10 步顺序与 BR-5 一致：**先渲染、再故障、再延迟**。

## 7. 一致性清单（本设计如何满足业务规则）

| 规则 | 实现点 |
| --- | --- |
| BR-4 匹配顺序稳定 | 快照构建时按 priority/created_at/key 预排序 |
| BR-5 注入顺序 | MockService 固定步骤 7→8→10 |
| BR-6 切换原子 | 快照 atomic 替换 + 事务内切换 |
| BR-7 记录 best-effort | 异步队列 + 降级直写 |
| BR-10 渲染不 panic | 模板引擎全程无 panic + Recover 中间件兜底 |
